# Running the classifier on the ESP32

Step-by-step, from a bare DevKit V1 to a live posture reading and a measured
accuracy number.

> **Nothing in this guide has been executed.** No board was connected and no
> toolchain was installed on the machine that built this project, so every
> output shown below is what you *should* see, not what was observed. The code
> paths it exercises are verified in software (`reports/phase9_audit/`), but
> compilation, upload and on-device timing are all **PENDING_HARDWARE** until
> you run them.

---

## 0. What you need

| | |
|---|---|
| Board | ESP32 DevKit V1 (30-pin) |
| Sensor | the existing 24 × 21 Velostat matrix with 4 × 74HC4067 multiplexers |
| Cable | USB data cable (not charge-only) |
| Driver | CP210x or CH340, depending on your board |
| PC | the project checkout + its `venv` |

**Wiring is unchanged.** The firmware uses exactly the pins the original
sketch used — verified mechanically, see §7.

| Signal | GPIO |
|---|---|
| `ROW_S0..S3` | 25, 26, 27, 14 |
| `COL_S0..S3` | 16, 17, 18, 19 |
| `ROW_EN_1`, `ROW_EN_2` | 21, 22 |
| `ROW_SIG` | 13 |
| ADC columns 0–15 | GPIO34 |
| ADC columns 16–20 | GPIO35 |

## 1. Install a toolchain

Neither PlatformIO nor arduino-cli is installed. Pick one — arduino-cli is
lighter.

### Option A — arduino-cli (recommended)

```powershell
winget install ArduinoSA.CLI
```

Close and reopen PowerShell so `arduino-cli` lands on `PATH`, then:

```powershell
arduino-cli config init
arduino-cli config add board_manager.additional_urls https://espressif.github.io/arduino-esp32/package_esp32_index.json
arduino-cli core update-index
arduino-cli core install esp32:esp32
```

The ESP32 core is a ~1 GB download. Verify:

```powershell
arduino-cli core list
```

You should see `esp32:esp32` with a version.

### Option B — PlatformIO

```powershell
pip install platformio
```

A ready-made `platformio.ini` is **not** included; if you go this route, point
it at `esp32/smart_cushion` with `board = esp32doit-devkit-v1` and
`framework = arduino`.

## 2. Assemble the sketch folder

The Arduino toolchain only compiles files sitting **beside** the `.ino`. The
shared C++ lives one level up, so copy it in:

```powershell
cd "C:\Users\Niranjana Gopinath\Projects\Smart-Cushion\esp32"

copy preprocess.h    smart_cushion\
copy preprocess.cpp  smart_cushion\
copy inference.h     smart_cushion\
copy inference.cpp   smart_cushion\
copy model_data.h    smart_cushion\
```

`smart_cushion\` should now contain exactly six files:

```
smart_cushion.ino     the scan loop + protocol + calibration
preprocess.h / .cpp   baseline subtraction, noise gate, clamp, scale
inference.h / .cpp    the INT8 kernel
model_data.h          generated weights — regenerate with ml\export_int8.py
```

> **Re-copy `model_data.h` every time you retrain.** It is generated by
> `ml\export_int8.py`; a stale copy in `smart_cushion\` will silently flash an
> old model.

## 3. Compile, and record the memory figures

```powershell
arduino-cli compile --fqbn esp32:esp32:esp32doit-devkit-v1 smart_cushion
```

Expected tail:

```
Sketch uses XXXXXX bytes (YY%) of program storage space. Maximum is 1310720 bytes.
Global variables use XXXXX bytes (YY%) of dynamic memory, ... Maximum is 327680 bytes.
```

**Copy those two lines into `reports/phase5_export/memory_budget.md`** under a
new *Measured on hardware* heading. The figures currently in that file are
derived from the generated header, not from a compiler — this is audit item
**H5**.

Sanity check against the prediction: the model contributes ~17.2 kB of flash
and the whole program ~32.1 kB of static RAM. Anything wildly different means
a stale or wrong `model_data.h`.

### If compilation fails

| Error | Cause |
|---|---|
| `model_data.h: No such file` | you skipped §2 |
| `SC_N_CLASSES undeclared` | `model_data.h` not copied, or truncated |
| `'lrintf' was not declared` | missing `#include <math.h>` — do not edit; re-copy `inference.cpp` |
| `region 'dram0_0_seg' overflowed` | the model is too large; shrink it and re-run `ml\export_int8.py` |

## 5. First run — calibration

**Take everything off the cushion before the board boots.** The firmware
calibrates at startup and will refuse a baseline captured under load.

```powershell
cd ..
.\venv\Scripts\Activate.ps1
python dashboard\serial_tester.py --port COM5 --seconds 30
```

Expected opening lines:

```
ESP32 matrix scanner ready
[INFO] smart-cushion firmware with on-device INT8 inference
[STATE] CALIBRATING
[INFO] Keep the cushion COMPLETELY UNLOADED until calibration finishes.
[CAL] 1/20
...
[CAL] 20/20
[CAL] OK
[STATE] READY
[INFO] Calibration accepted. You can sit down now.
```

Then one line per frame, about 1.4 per second:

```
frame    1  min= 112 max=4095 mean=2733.4   C3_Left_Lean  conf=0.712   4210 us  [ESP32]
```

`[ESP32]` means the label was computed **on the board**. That is the real thing.

### If calibration is refused

The firmware reports why and stays in `CALIBRATION_FAILED`, still streaming
frames but reporting `UNKNOWN` for every prediction. Clear the cause and type
`CAL` into the tester to retry.

| Result | Meaning | Fix |
|---|---|---|
| `PRESSURE_DETECTED` | something is resting on the cushion | clear it |
| `UNSTABLE_BASELINE` | readings drifting during the window | let it settle ~30 s after power-up |
| `EXCESSIVE_NOISE` | very noisy readings | check grounding and the mux wiring |
| `NO_SIGNAL` | all channels near zero | check `ROW_SIG` (GPIO13) and the row mux enables |
| `RAIL_SATURATED` | all channels pinned high | check the pull-down / series resistor |

## 6. Serial protocol and commands

115200 baud, one record per line.

| Line | Meaning |
|---|---|
| `FRAME,<504 ints>` | one raw ADC frame, row-major `row*21 + col` |
| `PRED,<label>,<confidence>,<inference_us>` | smoothed prediction |
| `STATE,<state>` | `CALIBRATING` / `READY` / `CALIBRATION_FAILED` |
| `CAL,<progress or result>` | calibration progress and outcome |
| `INFO,<text>` | free-form |

Commands (type and press enter in the tester, or use the dashboard buttons):

| Command | Effect |
|---|---|
| `CAL` | restart calibration |
| `MODE RAW` | stream `FRAME,` only, suppress predictions |
| `MODE PREDICT` | stream frames **and** predictions (default) |
| `STATUS` | print state, mode, model flash/RAM bytes, class list, smoothing window, threshold |
| `HELP` | list commands |

`<label>` is `UNKNOWN` when the smoothed top probability is below **0.55**, or
whenever calibration has not succeeded.

> ### Compatibility warning
> The `FRAME,` prefix **breaks** the original `PLOT.PY`,
> `collect_p2_same_structure.py`, `collect_p3_with_heatmap.py`,
> `collect_p4_with_heatmap.py` and the `RECAPTURE_*` scripts. They parse a bare
> comma-separated line and reject anything whose field count is not 504.
> `MODE RAW` does **not** restore the bare format — it only suppresses `PRED`.
>
> To collect more data with those scripts, either flash
> `esp32\backup_20261115\matrix_scanner_original.ino`, or change their
> `read_frame()` to strip a leading `FRAME,`.

## 7. Confirming the scan was not altered

The acquisition code is byte-identical in behaviour to your original sketch.
This is checked mechanically, not by eye:

```powershell
python ml\verify_firmware.py
```

Verifies all 17 pin/timing constants, that `setAddress()` and `readAverage()`
are identical after comment/whitespace normalisation, that the 18-operation
hardware sequence inside the scan matches in order, that the same 13
`pinMode()` calls are present, and that the ADC/serial configuration is
unchanged. Report: `reports/firmware_scan_diff.md` (currently **PASS**).

What changed and why: `esp32/FIRMWARE_CHANGES.md`. In short — the scan body
moved verbatim from `loop()` into `scanMatrix()` so inference can run *after* a
complete 504-value frame, with no statement reordered or retimed.

## 9. Measuring live accuracy (audit item H4)

```powershell
streamlit run dashboard\app.py
```

1. Sidebar → source **ESP32 serial** → pick the port → **Start test**.
2. Wait for `STATE,READY`. The banner turns green and says predictions are
   embedded inference. (On the simulated source it is yellow and says the
   opposite — do not mix the two up when reporting results.)
3. Seat the participant.
4. For each of the six postures:
   * choose the **actual** posture in the **Manual posture** dropdown,
   * hold it for ~15 seconds,
   * press **Log this comparison** roughly once a second — at ~1.4 Hz you get
     about 20 samples per posture.
5. Press **Download comparison CSV** and save to
   `reports/hardware_validation/<date>_<participant>.csv`.

The dashboard shows running agreement; the CSV has one row per logged frame
with the manual label, the predicted label, confidence and origin.

### Recruit people who are not P1–P4

All four are in the shipped model's training set. Testing on them measures
memorisation, not generalisation, and will give a misleadingly high number.

### What to expect, honestly

From `MODEL_CARD.md` §6, on participants the model has never seen:

* **Left lean and right lean should mostly work** (~0.64–0.70 recall).
* **Forward lean and backward lean will be badly confused with each other** and
  are close to unusable.
* **Normal frequently reads as slouching.**
* Overall accuracy on a new person is expected around **0.42–0.44** against a
  chance level of 0.167.

If you see much better than that on a *new* participant, check you are not
accidentally replaying recorded data (yellow banner / `[Python]` tag). If you
see much worse, suspect calibration or column 20 before suspecting the model.

## 11. Troubleshooting

| Symptom | Likely cause |
|---|---|
| No serial output at all | wrong port; charge-only USB cable; missing CP210x/CH340 driver |
| Garbled output | baud rate not 115200 |
| `FRAME,` lines but never `PRED,` | `MODE RAW` is active, or calibration failed — send `STATUS` |
| Every prediction is `UNKNOWN` | calibration failed (`STATUS` shows `CALIBRATION_FAILED`), or confidence is genuinely below 0.55 |
| Label lags the sitter by seconds | expected: ~1.4 Hz scan × 3-frame smoothing window ≈ 2 s |
| An entire column reads 0 | the column-20 fault (see `MODEL_CARD.md` §1) — reseat that mux connection |
| Predictions flip constantly | low confidence near the 0.55 threshold; the sagittal classes are known-weak |
| Dashboard shows 🟡 Python | you are on the simulated source, not the board |
